# 微信支付集成说明：直连与服务商模式

核对日期：2026-10-01。适用范围：微信支付 API v3、普通商户直连，以及普通服务商为特约商户接入小程序支付。

**当前仓库只实现直连模式。本文用于后续集成评估，不代表已经支持服务商模式；修改环境变量不能直接完成切换。** 本次不新增支付代码、模式开关、数据库迁移或服务商配置项。现有业务接入步骤见[支付、退款与对账指南](payment-integration.md)。

## 1. 两种模式有什么区别

| 维度 | 普通商户直连 | 普通服务商模式 |
| --- | --- | --- |
| 接入身份 | 使用当前收款商户身份调用微信 | 服务商代特约商户调用微信 |
| 收款商户标识 | `mchid` | `sub_mchid`；服务商另有 `sp_mchid` |
| 请求签名凭据 | 普通商户的 API 证书私钥及序列号 | 服务商的 API 证书私钥及序列号 |
| 应用与用户标识 | `appid` 与其对应的 `openid` | `sp_appid` / `sub_appid` 与相应的 `sp_openid` / `sub_openid` |
| 客户接入准备 | 普通商户支付权限、AppID 绑定和凭据 | 服务商资格、特约商户进件/签约、支付权限及相关 AppID 绑定 |
| 当前模板 | 已实现并完成直连联调 | 尚未实现，需要后端适配 |

给客户开发系统，并不自动意味着必须使用服务商模式。客户使用自己的普通商户号和凭据时，仍属于直连。服务商模式下，收款归属特约商户，不应理解为由服务商先收款再自行转账给客户；具体资金结算依商户协议执行。参见[服务商开发指引](https://pay.wechatpay.cn/doc/v3/partner/4012076732)。

本文不覆盖平台收付通、合单支付、分账或商户进件系统的开发。这些能力需要独立评估，不能因为支持服务商支付就认为同时具备。

## 2. 本项目的部署前提

已确认：每个客户独立部署、独立数据库，服务器由我们团队管理。若后续接入服务商模式，每套实例固定配置当前客户的特约商户身份，不引入多租户或客户端动态选择收款商户。

适配完成后的目标是共用代码和镜像，由服务端配置选择直连或服务商实现。当前仍按直连配置部署。服务商私钥等凭据由团队在运行环境注入，不放入 Git、镜像、小程序或业务接口响应。多个实例使用同一服务商身份时，凭据轮换需要协调所有相关实例。

独立部署并不会缩小同一服务商凭据在微信侧的权限范围。必须在应用层固定并核对特约商户归属；日志应保留用于排查的订单号与状态，不输出签名私钥、API v3 密钥或完整敏感报文。

## 3. 当前直连模式所需参数

以下是**代码已经读取**的配置，来源见 `apps/api/src/common/config/app-config.ts`：

| 环境变量 | 含义及来源 |
| --- | --- |
| `WECHAT_APP_ID` | 当前客户小程序 AppID；支付配置也使用此值 |
| `WECHAT_APP_SECRET` | 小程序登录所需 AppSecret，用于服务端获取用户 openid，不是支付签名密钥 |
| `WECHAT_PAY_MCH_ID` | 当前普通收款商户号 |
| `WECHAT_PAY_MERCHANT_SERIAL` | 该商户 API 证书序列号 |
| `WECHAT_PAY_MERCHANT_PRIVATE_KEY` | 与证书匹配的商户私钥 PEM |
| `WECHAT_PAY_API_V3_KEY` | 该商户配置的 API v3 密钥，用于通知解密 |
| `WECHAT_PAY_PUBLIC_KEY_ID` | 微信支付公钥 ID，当前实现按公钥模式验签 |
| `WECHAT_PAY_PUBLIC_KEY` | 与该 ID 对应的微信支付公钥 PEM |
| `WECHAT_PAY_NOTIFY_URL` | 支付通知公网 HTTPS 地址，映射到 `/payments/wechat/notify` |
| `WECHAT_PAY_REFUND_NOTIFY_URL` | 退款通知公网 HTTPS 地址，映射到 `/payments/wechat/refund-notify` |

当前 `WECHAT_PAY_MCH_ID` 留空时不加载支付模块；填写后须满足完整配置校验。商户 API 证书序列号与微信支付公钥 ID 用途不同，不能互换：前者说明请求由哪个商户证书对应私钥签名，后者用于选择验签的微信支付公钥。

金额、订单号、退款单号、用户 openid 等是交易过程中生成或获取的数据，不是可供所有订单共用的静态环境参数。业务金额由服务端确定，使用整数分。

## 4. 服务商模式需要准备的资料

下表使用微信接口字段或资料名称，**不是当前项目已支持的环境变量**。未来实施时再确定配置命名及校验规则，不要把服务商资料直接塞入现有直连字段后上线。

| 参数或资料 | 谁提供、用于什么 |
| --- | --- |
| `sp_mchid` | 我们的微信支付服务商商户号，用于服务商身份 |
| `sp_appid` | 与服务商商户号具有所需绑定关系的 AppID |
| `sub_mchid` | 当前客户进件后获得的特约商户号，是本实例固定的收款身份 |
| `sub_appid` | 客户小程序 AppID；客户自有小程序场景需准备，并完成与特约商户的绑定 |
| 服务商 API 证书序列号及私钥 | 用于服务商请求签名，不能使用客户普通直连商户的私钥替代 |
| 服务商 API v3 密钥 | 用于该服务商通知的解密 |
| 微信支付公钥 ID 与 PEM | 按服务商接入配置准备，用于响应和通知验签；延续当前公钥模式时需要核对可用性 |
| 支付、退款通知地址 | 分别指向当前客户实例的公网 HTTPS 入口 |
| 客户小程序 AppSecret | 独立登录流程仍需使用，与支付服务商密钥分开管理 |
| `sub_openid` 或 `sp_openid` | 登录过程获取的用户标识，按所属 AppID 选择，不配置为固定值 |

商户号、AppID 的角色及绑定要求以[微信开发必要参数说明](https://pay.wechatpay.cn/doc/v3/partner/4013080340)为准。接口签名、微信公钥验签和通知解密是三个不同步骤，切换模式时应一起核对凭据归属。

### AppID 与 openid 必须成对

按当前“客户拥有自己的小程序”的接入场景，用户通过客户小程序登录取得的 openid 应作为 `sub_openid` 使用，并匹配客户的 `sub_appid`。如果未来改用服务商的小程序，则需要重新确认 `sp_appid` 与 `sp_openid` 的组合，不能把同一个 openid 随意放入另一字段，更不能使用 unionid 替代。

普通服务商 JSAPI/小程序下单接口为 `POST /v3/pay/partner/transactions/jsapi`，直连接口为当前代码使用的 `POST /v3/pay/transactions/jsapi`。服务商字段和条件见[官方下单文档](https://pay.wechatpay.cn/doc/v3/partner/4012759974)。官方另列有“小程序支付（新）”产品文档；正式实施时应按实际开通产品选择完整接口体系，避免混用参数和调起协议。

## 5. 后续需要调整哪些代码

以下是基于当前仓库的改动清单，均未在本次实施。

| 位置 | 当前行为 | 服务商适配要点 |
| --- | --- | --- |
| `apps/api/src/common/config/app-config.ts`、`apps/api/src/app.module.ts` | 按直连参数加载，依据 `WECHAT_PAY_MCH_ID` 启用模块 | 增加模式选择及对应配置校验，调整启用条件，明确签名身份与收款身份 |
| `apps/api/src/modules/payments/payments.module.ts` | 注入单一网关和配置 | 根据模式选择接入实现，继续保持统一业务入口 |
| `apps/api/src/modules/payments/wechat-pay.gateway.ts` | 使用直连下单/查单/关单参数和身份字段 | 适配服务商端点、请求签名、用户标识、退款及账单参数，将结果转换为统一内部结构 |
| `apps/api/src/modules/payments/payment.service.ts`、`wechat-pay.crypto.ts` | 使用当前 AppID 签发调起参数，校验直连 `appid` / `mchid` | 使用实际调起小程序的 AppID 和正确签名身份；通知及补查核对服务商、特约商户、订单、金额和状态 |
| `apps/api/src/modules/payments/refund.service.ts` | 以直连商户身份验证支付和退款 | 退款沿用原支付的商户上下文，保留部分退款额度控制、幂等及异常状态追踪 |
| `apps/api/src/modules/payments/reconciliation.service.ts`、`trade-bill.parser.ts` | 按直连 AppID、商户号和账单列解析 | 按特约商户下载和核对账单，验证服务商账单列与身份，不直接沿用直连列假设 |
| `apps/api/prisma/schema.prisma` | Payment 未保存支付模式或商户身份快照 | 如需支持上线后切换模式，新增模式、商户/AppID 归属及配置引用；退款与对账关联原始身份 |
| 小程序支付封装、演示页和集成测试 | 接收后端调起参数，轮询平台支付状态 | 尽量保留统一前端流程，重新验证 AppID、签名、取消、重复点击和回查行为 |

上表中支付与对账文件名均位于 `apps/api/src/modules/payments/`，除已写明其他目录的路径外。

建议未来让直连实现和服务商实现承担微信接口差异，通用支付层继续管理状态、幂等、部分退款、业务事件和补查。业务仍决定商品信息、服务端价格、可退规则及履约。

### 退款和通知不能遗漏

服务商退款仍使用 `/v3/refund/domestic/refunds`，但需要带入对应 `sub_mchid`；查询退款也应按服务商接口要求携带归属信息，不能仅因为路径相似就复用直连请求。参见[服务商申请退款](https://pay.wechatpay.cn/doc/v3/partner/4012760121)。

支付通知需在验签和解密后校验服务商及特约商户身份；退款通知按其实际字段校验原支付归属、退款单及金额。不能简单移除现有 `mchid` 校验来兼容服务商。服务商 API v3 密钥用于其通知解密，具体字段随所用产品文档核对，参见[服务商支付通知说明](https://pay.wechatpay.cn/doc/v3/partner/4012886152)。现有 NestJS 通知入口可继续承接，无需因此新增独立通知服务。

### 每个客户的对账范围要隔离

服务商交易账单接口可指定 `sub_mchid` 获取单个特约商户账单；不传时可能取得服务商下所有子商户的全量账单。因此客户独立实例应限定自己的对账范围，不能直接沿用当前未传子商户号的下载请求。

官方对小微商户列有例外：不能用该参数取得单独账单，需要全量账单。若客户属于此类，必须重新评估账单获取与隔离方式，不能把其他客户账单放入该实例。参见[所有/单个子商户交易账单](https://pay.wechatpay.cn/doc/v3/partner/4012760132)。

## 6. 已有直连订单如何处理

当前模型没有持久化完整支付身份，不能认为更新配置后旧订单就会自动支持退款和查询。未来若要从直连迁往服务商模式，建议：

1. 为历史订单依据实际部署记录回填直连身份，不依赖新配置猜测。
2. 新订单使用新模式；旧订单的退款、关闭、查询和对账继续使用原始身份。
3. 保留仍需处理的旧模式凭据及通知验证能力；一个模式开关不能解决历史订单路由。
4. 密钥保存在运行环境或受控凭据存储中，数据库只保存身份和配置引用，不保存私钥。

若不实现双模式历史处理，就需要另行安排旧实例继续处理历史交易，不能直接覆盖凭据停掉旧链路。独立客户部署与历史支付身份管理是两个问题。

## 7. 将来实施时的验证范围

以下用于评估交付完整性，当前不执行服务商开发或真实交易：

- 直连回归：已有支付、退款、补查和对账继续通过。
- 身份校验：错误的服务商、特约商户、AppID、签名、金额和通知归属必须拒绝。
- 支付全流程：预支付、真机调起、主动查单、通知先后到达、关闭及重复请求。
- 退款：多次部分退款、累计金额约束、重复通知、请求结果未知与异常退款处理。
- 对账：只核对当前客户账单，校验列格式、金额单位、日期和商户身份。
- 历史订单：如支持切换，验证旧直连订单和新服务商订单分别查询、退款及对账。

最终需要真实服务商与特约商户完成小额支付、退款、两类公网通知和次日账单验证。受控响应测试不能代替真实接入验收。
