# 微信小程序全栈模板设计

日期：2026-09-27

## 目标与使用方式

为内部团队提供一个可复制、可改造的微信小程序全栈模板。每个新业务从模板创建独立仓库或项目，替换门户页面，增加自己的业务模块，并使用模板内已经实现的通用能力。业务之间不共享运行时，也不引入多租户模型；未来出现明显不同的场景时，可以在此基础上新增模板。

首版只交付微信小程序运行能力，但将平台调用集中在清晰边界内，方便未来新增其他端的实现。首版门户仅提供导航和页面骨架，不预设行业视觉或业务内容。

## 范围与职责边界

模板交付一个 monorepo，而不是单独的前端包：

- `apps/miniapp`：Taro、React、TypeScript 小程序。提供门户骨架、请求与会话接入、基础状态和存储、路由规则，以及微信能力的页面调用示例。
- `apps/api`：NestJS 服务。通过 Prisma 使用 PostgreSQL，接入阿里云 OSS 和微信平台服务，直接实现通用后端流程。
- `packages/contracts`：前后端共同使用的接口数据与错误码类型。只共享稳定的传输契约，不共享业务实现或 Prisma 内部模型。

团队复制模板后，业务负责商品及其他业务元数据、业务订单、定价和可购买规则、退款决策与金额规则、履约，以及专有页面和 API。模板负责微信支付下单、支付结果确认、退款请求与结果确认、支付记录及账单核对。这里的“下单”指调用微信支付创建预支付交易，不指创建通用业务订单。模板不提供购物车、优惠券、运费、配送、发票或商品管理系统。

## 模块边界与数据流

### 身份与用户

小程序通过微信登录取得临时凭证，API 服务向微信换取身份标识，查找或创建本地用户，再签发业务会话。小程序请求层携带会话信息；会话过期时执行统一续期，续期失败则清除本地会话并回到登录入口。需要登录的页面通过统一路由规则控制。

手机号和用户资料是登录后的独立、由用户主动触发的操作，不作为登录成功的条件。后端保存业务确需使用的数据；小程序侧不保存微信服务端密钥。

### 请求、状态与错误

请求层统一处理 API 地址、会话附加、超时、错误映射和会话失效。前后端通过共享契约定义稳定的请求与响应结构。全局状态只保存跨页面必需的信息，如会话和当前用户；业务状态归业务模块。环境配置区分本地开发与测试联调，不在源码中写入密钥。

### OSS 文件

小程序选择图片后，请求 API 服务生成短时、限定文件大小、类型和对象路径的上传授权，随后直传 OSS，并向 API 确认文件。后端验证登录身份、授权范围与最终对象，持久化文件记录；长期 OSS 凭证只留在服务端。模板提供完整的选择、上传、确认和错误处理示例；文件实际用途由业务决定。

### 微信原生能力

提供登录、用户资料与手机号、分享、图片选择与上传、支付等能力的明确调用入口及示例。页面负责触发需要用户操作或授权的能力。只对需要统一错误、后端协作或业务契约的能力进行封装；Taro 已经足够清晰的 API 直接使用，避免建立一层机械代理。门户使用 Taro 基础组件和少量自有基础组件，不预装完整 UI 组件库。

### 支付、退款与对账

业务服务验证自己的业务订单、价格和退款规则后，向通用支付模块提交支付或退款请求。支付模块保存支付交易及退款记录，调用微信支付接口，返回小程序调起支付所需参数，并处理微信异步通知。小程序返回前台后向 API 查询最终状态；前端支付回调本身不作为最终到账依据。

支付和退款通知必须校验来源与内容，并以交易号、退款号保证幂等。支付模块提供主动查单与退款查询，以处理通知延迟或丢失。账单核对按微信交易账单与本地支付、退款记录比对，记录差异供团队处理；首版不建设运营后台。业务订单状态及履约由业务模块依据可信的支付状态自行更新。

### 日志与埋点

小程序将约定格式的事件和错误上报给 API。API 使用 Winston 对请求、应用事件和错误做基础分类，输出适合 Docker 收集的结构化日志。首版不建设 ELK、Grafana、独立分析数据库或查询后台；不得把会话令牌、支付密钥、手机号等敏感值写入日志。

## 开发与部署

monorepo 使用 workspace 管理两个应用和共享契约，提供统一的安装、构建、检查与迁移命令。API 提供生产镜像构建文件；本地使用 Docker Compose 运行 PostgreSQL 等开发依赖，API 可本地运行或容器运行。Prisma 迁移纳入部署流程。

微信小程序、微信支付和 OSS 的开发凭证可由测试环境提供；本地中间件使用 Docker 配置。凭证通过环境变量或部署密钥注入，仓库只提交变量示例。真实支付通知联调需要一个微信可访问的测试回调地址；本地测试可以使用模拟通知覆盖处理逻辑，但不能替代真实联调。

## 分阶段交付与验收

1. **仓库底座与身份**：建立 workspace、Taro、NestJS、Prisma、PostgreSQL、共享契约和 Docker 基础；打通登录、会话续期、用户资料、请求与路由。验收为前后端构建通过、迁移可执行、登录链路可用、会话失效行为可验证。
2. **文件与微信能力**：实现 OSS 授权直传及确认、图片选择、手机号、分享、日志与埋点接入。验收为正常、拒绝授权、上传失败及重试路径可验证。
3. **支付能力**：实现微信支付下单、调起、通知、查单、退款、退款通知与查询、账单核对和差异记录。验收包括重复请求与通知、延迟回调、支付失败、退款失败和账单差异。
4. **模板交付**：完成可替换门户骨架、能力示例、内部复制指引、环境配置说明和整体构建验证。

外部服务流程先用受控响应验证关键分支；有可用的开发凭证与回调地址时，再在测试环境完成真实联调。每阶段保持可构建，避免把未完成的后续能力伪装成已可用能力。
