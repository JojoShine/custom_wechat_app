# 第三阶段：微信支付、退款与对账设计

日期：2026-09-27

## 目标与边界

为内部团队可复制的全栈小程序模板实现普通直连商户的微信小程序支付闭环。模板直接提供预支付、调起参数、可信支付结果、退款申请与结果、主动查单、每日对账及差异记录。模板内另设一个可删除的演示业务模块，以固定测试商品和服务端价格完成真实联调。

业务模块拥有商品及其他业务元数据、业务订单、定价、可购买规则、退款决策和金额规则、履约。通用支付模块不保存商品目录，不代业务创建订单，不决定是否允许退款，也不提供购物车、优惠券或运营后台。支付模块的“下单”专指向微信创建预支付交易。

本阶段只支持微信小程序、人民币、普通直连商户；其他支付渠道和服务商模式不在首版范围内。保留支付服务与微信适配器之间的边界，未来新增渠道时不要求业务模块读取微信协议字段。

## 方案选择

选择由业务服务调用通用支付服务。业务服务先验证业务订单及服务端价格，再提交不可由客户端修改的支付意图。支付服务负责交易持久化、微信协议、状态确认与事件投递。

让小程序直接向通用下单接口提交金额会绕过业务定价；让通用支付服务读取不同业务的订单表则会把业务模型写死在模板中。两者均不采用。业务对支付状态的处理采用持久化事件和幂等消费，避免通知处理成功但业务更新丢失。

## 组件与接口

- `apps/api` 的支付模块：业务侧服务接口 `createPrepay`、`getPayment`、`requestRefund`、`getRefund`；微信 API v3 适配器；支付及退款通知入口；到期支付单和处理中退款的主动查单；对账任务与指定日期重跑命令；支付状态事件投递。
- `apps/api` 的演示业务模块：固定测试商品、服务端标价、演示业务订单、购买及退款规则、支付事件消费者。演示入口默认关闭，只能显式在联调环境开启；退款只能针对当前用户自己的演示订单，并由服务端判断金额。复制模板时可删除整个演示模块，不影响通用支付模块。
- `apps/miniapp`：演示购买、调起 `Taro.requestPayment`、查询结果、演示退款和查看退款状态的页面与调用函数。客户端只传演示商品或业务单据标识，不传可信金额。
- `packages/contracts`：小程序可见的支付调起参数、支付与退款状态、演示业务请求和响应类型；不共享 Prisma 模型、商户密钥或微信通知原文。

通用服务接收业务命名空间、业务订单 ID、用户 ID、服务端确定的金额（分）、简短交易描述和幂等键。支付模块查本地用户微信 `openid`，生成自己的商户订单号。业务订单状态变化由业务模块消费支付事件后决定；支付模块不直接修改业务订单。

## 支付流程与状态

1. 演示业务先持久化固定价格的业务订单，再调用支付服务。支付服务持久化支付单，使用微信普通直连商户的 `/v3/pay/transactions/jsapi` 创建预支付交易，返回小程序调起支付所需的签名参数。小程序 `appid`、登录用户的 `openid`、商户号、金额、通知地址均由服务端填入。
2. 同一业务订单的并发或重复请求只对应一个当前支付尝试。金额或用户与已存在尝试不一致时拒绝；调用微信结果未知时先按同一商户订单号查单或重试，不生成另一个收款单。未支付且已到期的尝试经微信查单并关单后，业务可以显式发起新的支付尝试；已支付的业务订单不得再次发起。
3. 小程序支付回调只表示本地调用结束。页面随即向 API 查询状态；服务端在待定状态下向微信查单。微信支付通知经原始请求体验签、解密并核对 `appid`、`mchid`、商户订单号、微信交易号、金额和币种后，才推进本地状态。查询接口的微信响应也必须验签。重复、乱序或延迟通知不能使终态回退，也不能重复触发业务事件。
4. 支付单至少区分待创建、待支付、已支付、已关闭、支付失败和待核实状态。调用微信超时或结果不明保持待核实，直至查询或通知确认；不得把网络错误直接当作未付款。到期未付单由后台查询并在确认未付后关单。
5. 支付状态变化与待投递事件在同一数据库事务内保存。事件投递失败可重试；业务消费者以事件 ID 和业务订单 ID 幂等处理。演示业务据此更新自身订单。业务也可按业务单据关联查询支付状态，用于人工恢复。

## 退款流程与状态

业务服务先判断是否允许退款及本次金额，再以业务退款 ID 作为幂等依据请求支付模块。支付模块先向微信确认原交易已支付，随后在数据库中原子预留本次退款额：所有成功、处理中、异常或结果不明的退款预留额之和不得超过原支付金额。同一业务退款 ID 重试使用同一商户退款单号；不同业务退款 ID 可以创建多次部分退款。遵守微信每笔交易最多 50 次部分退款及两次申请间隔要求。

调用微信退款接口返回受理只进入处理中。退款通知需验签、解密，并核对商户号、支付单号、退款单号、原单金额和本次退款额；主动查询补偿漏通知。`SUCCESS` 是成功终态；`CLOSED` 释放该笔预留额，业务如仍需退款须以新的业务退款 ID 重新申请；`ABNORMAL` 保留预留额并记录告警，由团队在微信商户平台处理，之后继续查单。微信请求超时或不确定结果保持待核实并用同一退款单号查询，不能换号盲目重试。退款状态变化同样通过持久化事件通知业务。

## 对账与异常处理

每日北京时间 10 点后自动申请前一日的微信 `ALL` 交易账单；提供指定日期重跑命令。下载前验证微信返回的账单链接与摘要，下载后按响应中的哈希类型和值校验文件，再解析明细。仅接受微信官方账单字段及金额格式，按商户订单号、商户退款单号和金额逐笔对比。支付行是支付成功交易；退款行是退款申请受理记录，不能用它推断最终退款成功。退款最终状态始终以通知或退款查单为准。

每次对账保存日期、运行状态、账单摘要、汇总和差异明细，包括微信有而本地无、本地有而微信无、金额不符及状态不符。重跑生成新运行记录，不覆盖历史；最新成功运行供团队查看。账单未生成、请求失败、哈希不符或解析失败均记为任务失败并重试，不记作零交易。微信明确当天无账单时，只有本地也无预期交易才记为无差异；本地有预期交易则记差异。对账失败和未解决差异以现有 Winston 结构化日志告警，不建立运营后台。

自动任务在单个 API 实例内调度；数据库锁和日期级幂等使多个实例同时运行时只有一个执行者。自动任务失败后重试，团队也可按日期重跑。微信只提供近三个月的在线账单，重跑命令明确拒绝超出可下载范围的日期。

## 安全与配置

采用微信支付 API v3 的普通直连商户接口与公钥验签模式。环境变量提供商户号、商户 API 证书序列号和私钥、API v3 密钥、微信支付公钥 ID 和公钥、支付及退款回调 URL。密钥不提交仓库，不回传小程序，也不进入日志。服务端对微信请求签名，对所有可验签 API 应答及两类通知验签；回调以原始请求体验签后才解密，未知公钥 ID 或签名失败直接拒绝。回调不依赖客户端会话，但严格校验身份字段及本地支付记录。支付查询和退款查询的客户端接口仅允许订单所属用户访问；后台重跑命令仅供部署环境中的团队使用，不暴露公开 HTTP 管理入口。

演示支付默认禁用，需显式设置环境开关；联调时使用固定低额测试商品和独立测试凭证。真实支付通知需要微信可访问的 HTTPS 回调地址。Docker API 镜像继续使用现有构建与环境注入方式。

## 验收与限制

自动化测试覆盖签名验签与解密、金额及身份不符通知、重复和乱序通知、重复及并发预支付、支付调用失败和不确定结果、主动查单及关单、重复和并发部分退款、累计额度与次数限制、退款受理后失败或异常、账单校验与差异、任务重跑和业务事件重试。前后端类型检查、测试、构建和 Docker 镜像构建均须通过；Prisma 迁移与生成使用本机 nvm 的 Node 22.23.2 验证。

有商户凭证、公钥和公网回调地址时，另做真实低额支付、退款及通知联调，并记录实际验证的链路。若这些外部条件暂缺，交付仍包括完整实现与受控外部响应测试，但不得宣称真实微信链路已跑通。异常退款由微信商户平台人工处理；本阶段负责记录、告警和持续状态核实，不收集银行卡资料或调用异常退款 API。
