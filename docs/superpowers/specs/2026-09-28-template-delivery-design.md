# 第四阶段：全栈模板交付设计

日期：2026-09-28

## 目标与边界

让团队成员直接复制本仓库，替换门户并接入自己的业务模块，能够沿用已实现的微信小程序、NestJS API、Prisma/PostgreSQL、私有 OSS、微信能力和支付能力。每个复制品是独立的单实例项目；第四阶段不增加多租户、通用商品或订单系统，也不制作模板生成器。

本阶段交付的是可操作的复制流程、清晰的替换边界和可验证的构建结果。真实微信登录、支付、退款及 OSS 联调需要外部凭证和可访问环境，留在本阶段交付之后执行；交付文档必须明确区分本地受控测试与真实联调。

## 复制与替换流程

团队直接复制仓库并保留 monorepo 结构。指引依次说明：修改项目及小程序展示名称；配置小程序和 API 环境变量；启动本地 PostgreSQL 并执行 Prisma 迁移；替换门户内容与导航；创建业务自己的数据模型、API 和页面；从业务服务调用平台支付与退款接口；注册可信支付事件以更新业务状态；按需关闭或移除演示模块；执行测试、构建和容器检查。

模板包名 `@template/*` 与数据库开发账号是仓库内部标识，复制后不要求立即重命名。指引要指出若团队选择重命名，必须同步更新 workspace 依赖、脚本、Dockerfile 和锁文件，避免只改显示名称造成构建失败。演示模块默认关闭；保留演示代码作为可删除的支付接入示例。已经部署的复制品删除演示数据表时，应新增迁移，不修改已执行的迁移历史。

## 门户与能力示例

门户保持中性且可直接替换，不引入行业视觉、商品入口或运营内容。门户只展示通用导航：个人资料、分享和开启后才出现的支付联调演示。导航路径集中维护，复制后的业务页面有明确的登记位置；受保护页面经过现有会话守卫，登录返回目标仍受允许路径约束。第四阶段只整理这条接入路径，不建设动态菜单系统。

个人资料页继续展示昵称、微信头像、相册图片、手机号和退出登录；分享由门户展示；演示业务展示支付、服务端状态查询及退款。这些页面和对应 API 是接入示例，业务专有页面和规则应由复制品增加。通用能力代码保持在现有 `core` 与后端模块内，避免将演示业务逻辑移入平台模块。

## 环境与交付文档

交付文档应为内部开发者提供一条从复制到本地验收的最短路径，以及按用途划分的环境变量表：本地中间件、微信小程序身份、OSS、微信支付、可关闭演示、小程序公开构建变量。明确哪些变量是服务端密钥，不能出现在小程序构建变量或仓库中；回调 URL 和微信合法域名分别对应何种用途。

本阶段结束时单独向用户提供真实联调参数清单，列出小程序身份、普通直连商户支付、公钥验签、OSS 私有 Bucket、域名与回调可达性等所需项，标注敏感字段和非密钥信息。清单不要求用户在第四阶段编码前提供密钥，也不在仓库中保存实际值。

## 验收

在现有单个本地 PostgreSQL 测试数据库上执行测试，不新建第二个数据库。使用 nvm 中的 Node 22.23.2，验证 `pnpm test`、`pnpm typecheck`、默认和开启演示的微信小程序构建、`pnpm build` 及 `pnpm test:container`。检查默认构建不包含演示入口，启用构建包含演示入口；复制指引中的路径、命令、变量名与当前代码一致。

验收结果如实记录。没有商户凭证、公网回调或 OSS 测试环境时，不宣称真实外部链路已经跑通。第四阶段完成后给用户参数清单，收到参数再安排真实联调。
